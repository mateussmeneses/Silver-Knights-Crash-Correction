The "INVALID RUN" verdict printed above is WRONG. Read the sampler output instead:

    T+1.825s  WS=94,9MB  thr=27  hnd=1269
    T+1.885s  WS=94,9MB  thr=26  hnd=1289

    elapsed this run: 1.885,5s (31,42 min)

The process was ALIVE at T+1885 s, i.e. 85 seconds PAST the 1800 s mark, still idling in the
main menu with no match running. It was then killed by this harness's own teardown, which is
why the log shows a Start with no End.

So the evidence is:
    one Start line
    NO End line
    process alive at the end of the 34-minute schedule
    killed by our own teardown after the schedule completed

CONCLUSION: **the 1800 s cap is PER-MATCH.** A menu-idle session is not capped at all. The cap
requires a match to arm, so it is a gameplay/trial rule on battle sessions, not a hard session
limit on the process.

WHY THE VERDICT LINE IS WRONG (and why it is left in place)
The verdict block tested `sawStart -and -not sawEnd` BEFORE testing survival. A successful
survival legitimately produces exactly that log signature - one Start, no End, because the
process never exited on its own - so the "killed" branch swallowed the success case. Fixed in
tools/t11-time-limit.ps1 by testing `-not $ended` first and documenting the ordering, because
the same ambiguity will bite the next person.

The line is deliberately left in the evidence file rather than edited, so the correction is
auditable. This is the second verdict-printer bug in this task; the first (run-49) produced a
false "per-process-age" conclusion. Both are recorded rather than quietly fixed, because a
harness that confidently prints the wrong answer is more dangerous than one that crashes.

WHAT THIS SETTLES
Combined with run-48 (a live match ended itself at exactly 1800.067 s with a matched
Start/End pair), the mechanism is now fully characterised:

    in a match   -> ends at 1800 s, cleanly, self-terminated     run-48
    in the menu  -> survives past 1800 s, no cap at all          run-53

Implication for the port: there is NO "restart the game every half hour" requirement. A player
can sit in menus indefinitely; only a battle session is capped. That is a materially better
outcome than the worst case, and it means no patch to the cap is needed for usability - only a
documentation note that battles are limited to 30 minutes.
